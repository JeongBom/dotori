# 스코프 규칙

도토리 프로젝트의 컨셉을 지키기 위한 규칙입니다.
클로드 코드는 이 규칙을 모든 작업의 가드레일로 사용합니다.

## 도토리의 핵심 가치

도토리는 "가족이 함께 쓰는 우리집 재고 관리 + 미리 알림" 앱입니다.

사용자가 답을 얻고 싶은 질문은 단 세 가지입니다:
1. 지금 우리집에 뭐가 있나? (재고)
2. 곧 떨어지거나 상하는 게 뭐지? (알림)
3. 마트 가는 김에 뭐 사야 하지? (장보기)

이 세 질문에 답하지 못하는 기능은 도토리에 추가하지 않습니다.

## 절대 추가하지 않는 기능 (Non-goals)

다음 기능들은 도토리의 핵심 가치와 무관하므로 추가하지 않습니다.
사용자가 요청하더라도 우선 핵심 가치와의 연관성을 묻고 확인합니다.

- ❌ 가계부, 자산 관리, 지출 추적
- ❌ 일정 관리, 집안일 관리, 루틴 트래킹
- ❌ 레시피 추천, 요리 가이드
- ❌ 영양 정보, 칼로리 계산, 다이어트 기능
- ❌ 자동 발주, 쇼핑몰 연동 (쿠팡/마켓컬리 등)
- ❌ 가격 비교, 최저가 추적

## 추후 발전 영역 (MVP 이후 검토)

다음은 가치가 있지만 MVP 단계에서는 추가하지 않습니다.
앱 안정화 이후 별도 결정합니다.

- 🟡 바코드 스캔 입력
- 🟡 품목별 커스텀 알림 임계점 설정
- 🟡 가족 알림 우선순위 (담당 구매자 지정 등)
- 🟡 위치 기반 알림 (마트 근처 가면 장보기 알림 등)

## 기능 추가 요청 받았을 때 절차

사용자가 새 기능 추가를 요청하면 반드시 다음 순서로 진행합니다:

### Step 1: Non-goals 확인
요청받은 기능이 위 "절대 추가하지 않는 기능" 리스트에 있는지 확인.
있다면 사용자에게 알리고 거절 사유를 설명한다.

### Step 2: 핵심 가치 적합성 검토
요청받은 기능이 다음 세 질문 중 하나에 직접 답하는가?
- 지금 우리집에 뭐가 있나?
- 곧 떨어지거나 상하는 게 뭐지?
- 마트 가는 김에 뭐 사야 하지?

직접 답하지 못하면 "이 기능이 도토리의 핵심 가치에 어떻게 기여하는지" 사용자에게 묻는다.

### Step 3: 추후 발전 영역 확인
"추후 발전 영역" 리스트에 있는 기능이라면, 사용자에게 알리고
"MVP 안정화 이후에 추가하는 게 좋겠다"고 제안한다.

### Step 4: 트레이드오프 제시
새 기능 추가 시 사용자에게 다음을 명확히 알린다:
- 어떤 기존 코드가 영향받는가
- 어떤 새로운 복잡도가 생기는가
- 무엇을 빼야 균형이 맞을 것 같은가 (스코프 보호)

## 도토리답지 않은 작업 거절 예시

다음과 같은 요청이 들어오면 정중히 거절하거나 재검토를 제안한다:

- "월별 지출 그래프 추가해줘" → 가계부 영역, Non-goal
- "냉장고 음식으로 만들 수 있는 레시피 추천해줘" → 레시피 영역, Non-goal
- "이번 주 청소 일정 관리 기능 넣어줘" → 일정 영역, Non-goal
- "쿠팡에서 자동 주문되게 해줘" → 자동 발주, Non-goal
- "음식 칼로리 계산해서 보여줘" → 영양 관리, Non-goal

## 핵심 원칙

도토리는 "많은 일을 하는 앱"이 아니라 "한 가지를 잘하는 앱"이다.

기능을 추가하는 것보다, 핵심 기능을 더 잘 다듬는 것이 항상 우선이다.
