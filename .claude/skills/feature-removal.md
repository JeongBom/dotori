# 기능 제거 워크플로우

도토리에서 안 쓸 기능을 안전하게 제거하는 표준 절차입니다.
이 절차는 v1의 "한 번에 너무 많이 지워서 망함" 사고를 막기 위해 정의되었습니다.

## 사용 시점

다음 작업을 할 때 이 워크플로우를 따른다:
- v1 잔재 기능 제거 (가계부, 일정/집안일 등)
- MVP에서 빠지는 기능 정리
- 사용자가 "X 기능 제거해줘"라고 명시한 경우

## 사전 조건 체크

작업 시작 전 반드시 확인:

- [ ] git status가 clean한가? (커밋되지 않은 변경사항 없음)
- [ ] 현재 작업 브랜치가 main이 아닌가? (전용 브랜치 사용)
- [ ] CLAUDE.md의 "보호 대상" 영역을 건드리지 않는가?
  - 인증 (auth)
  - 가족 관리 (families, users, user_settings)
  - 음식 관리 (food_database, fridge_items)
  - 생필품 관리 (supplies)

위 조건 중 하나라도 만족하지 않으면 사용자에게 알리고 작업 중단.

## 절차

### Step 1: 영향 분석 (코드 안 건드림)

제거할 기능과 관련된 모든 것을 파악한다.

수행할 작업:
1. 제거할 기능의 화면 컴포넌트 파일 찾기
2. 해당 화면에서 사용하는 컴포넌트, 유틸 함수 추적
3. 관련된 Supabase 테이블 식별
4. 다른 화면에서 import하는 곳 확인 (의존성)
5. 라우터/네비게이션에 등록된 위치 확인

출력 형식:

```
## 영향 분석: [기능 이름] 제거

### 삭제 대상 파일
- screens/FinanceScreen.tsx
- components/AssetCard.tsx
- ...

### 다른 기능과 공유되는 파일 (주의)
- utils/formatCurrency.ts (가계부 + 자산만 사용, 삭제 OK)
- lib/supabase/assets.ts (이 기능 전용, 삭제 OK)

### 관련 DB 테이블 (보존, CLAUDE.md 정책에 따라)
- assets, asset_histories, goals, goal_items

### 라우터 변경 필요
- App.tsx의 FinanceScreen 라우트 제거 필요

### 예상 영향
- 영향받는 다른 기능: 없음
- 사용자에게 보이는 변화: 하단 탭에서 '자산' 탭 사라짐
```

이 분석을 사용자에게 보여주고 확인 요청. 사용자가 OK 하면 Step 2.

### Step 2: 백업

제거 작업 전 반드시:

1. 새 git 브랜치 생성 (예: `feature/remove-finance`)
2. 현재 상태 커밋: `git commit -m "before removing [기능명]"`

이 단계는 사용자가 직접 실행하도록 안내한다.
(클로드 코드가 git 명령을 자동 실행하지 않는다.)

### Step 3: UI 진입점 먼저 숨기기

코드 삭제 전에 사용자 진입을 막는다.

수행할 작업:
1. 하단 탭 네비게이션에서 해당 탭 제거 (또는 주석 처리)
2. 다른 화면에서 해당 기능으로 가는 버튼/링크 제거
3. 라우터에서 해당 라우트 제거

이 단계 후 확인:
- 앱이 정상 빌드되는가?
- 다른 화면들이 정상 동작하는가?
- 사용자가 해당 기능에 접근할 수 없는가?

✅ 통과 시 Step 4로. ❌ 문제 발생 시 즉시 git checkout으로 복원.

### Step 4: 컴포넌트 파일 단계적 삭제

⚠️ **한 번에 5개 이상 파일을 삭제하지 않는다** (safety.md 규칙)

수행할 작업:
1. 메인 화면 컴포넌트 삭제 (예: FinanceScreen.tsx)
2. 해당 화면 전용 보조 컴포넌트 삭제 (예: AssetCard.tsx)
3. 매 삭제 후 빌드 확인

5개 이상 파일이 있다면 여러 단계로 나누어 진행한다.
각 단계마다 빌드 확인 + git commit.

### Step 5: 로직/유틸 정리

수행할 작업:
1. 해당 기능 전용 유틸 함수 삭제
2. 해당 기능 전용 Supabase 쿼리 함수 삭제 (lib/supabase/)
3. 타입 정의에서 해당 기능 관련 타입 제거
4. AsyncStorage 키, Context 항목 정리

각 단계마다 빌드 확인.

### Step 6: DB 처리 결정 (CLAUDE.md 정책)

CLAUDE.md의 "DB 테이블 구조 > 보존" 정책을 따른다:
- 가계부 관련 테이블 (assets, asset_histories, goals, goal_items): **DB에서 삭제하지 않음**
- 일정 관련 테이블 (routines): **DB에서 삭제하지 않음**
- 이유: 데이터 보존, 추후 결정

이 단계에서 사용자에게 안내:
"DB 테이블은 보존 정책에 따라 삭제하지 않았습니다. 
가지치기 작업 안정화 후 별도 결정하시면 됩니다."

### Step 7: 최종 검증

다음 항목을 모두 확인:
- [ ] 앱이 정상 빌드되는가?
- [ ] iOS/Android에서 실행되는가?
- [ ] 보호 대상 기능(인증, 가족, 음식, 생필품)이 모두 정상 동작하는가?
- [ ] 콘솔에 새로운 에러가 없는가?
- [ ] 빈 상태(데이터 없음)에서도 정상인가?

리뷰어 페르소나로 자동 검토 호출:
"@.claude/agents/reviewer.md 페르소나로 이번 제거 작업을 검토해줘"

### Step 8: 마무리 커밋

최종 커밋 메시지:

```
remove: [기능 이름] - [짧은 이유]

- 영향 분석: X개 파일 제거
- DB 테이블 보존: assets, ...
- 보호 대상 기능 정상 확인
```

## 절대 금지 사항

다음은 어떤 경우에도 하지 않는다:

- ❌ Step 1 영향 분석 없이 바로 파일 삭제
- ❌ 한 번에 5개 이상 파일 삭제
- ❌ git 백업 없이 작업 진행
- ❌ 보호 대상 영역의 파일 삭제
- ❌ DB 테이블 DROP (보존 정책)
- ❌ 사용자 확인 없이 자동 진행

## 출력 의무

각 Step 시작 시 사용자에게 알린다:
"이제 Step X를 진행합니다. [내용 요약]"

각 Step 완료 시 결과를 보고한다:
"Step X 완료. [수행한 내용]. 다음 단계로 진행할까요?"

사용자가 "yes" 또는 명시적 동의를 표할 때만 다음 단계 진행.
